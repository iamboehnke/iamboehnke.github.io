Kroner og renter

Every weekday morning, Danish exchange and policy rates are fetched, checked and published as one dataset for a widget, an API and a database, and bad data is stopped before it reaches any of them.

Started October 2026

Python, Azure Functions, ADLS Gen2, Azure SQL, Medallion architecture, Data contracts, Django, GitHub Actions
View on GitHub

What it does

Every weekday morning, an Azure Function fetches Danmarks Nationalbank's exchange rates and policy rates from Statistics Denmark's open API, runs them through a medallion pipeline with quality checks, and publishes one data product that three consumers use: this page, a small Django API with a data catalogue, and an Azure SQL database.

I built it to learn Azure properly by doing the parts a data engineer is actually responsible for: loading data repeatedly without duplicates, stopping bad data before anyone uses it, and being able to say where every number came from. The widget below is the live end of the pipeline. It reads the published JSON straight from Azure.

Data sources

Both sources come from Statistics Denmark's StatBank API, free and without an API key: table DNVALD for exchange rates against the Danish krone, and table DNRENTD for the Nationalbank's policy rates. The API returns CSV with decimal commas and uses .. for missing values, so the pipeline parses and types them explicitly instead of trusting the format.

Late data is normal. DESTR, the overnight rate, is published a day after the others. The pipeline fetches an overlap of ten banking days on every run, so late and revised values arrive on the next run without creating duplicates.

Architecture

One timer-triggered Azure Function runs the whole pipeline. No servers to maintain and nothing running between runs.

Layer Where What happens
Bronze ADLS Gen2 The raw CSV is stored unchanged for every run, so any result can be traced back to the exact response it came from
Silver ADLS Gen2, Parquet Typed rows, merged on date and code so the same run can be repeated safely
Gold ADLS Gen2 and Azure SQL Readable names, daily change and history, the version the consumers use
Consumers JSON, Django, SQL This page, the API and catalogue, and SQL tables with a run id on every row

Data contracts and quality

Each data product has a YAML contract describing its schema, key, owner and expectations. The pipeline runs 15 checks from the contracts on every run, for example that the euro stays inside the ERM II band against the krone. A failed check with severity error quarantines the batch instead of publishing it, and the consumers keep serving the last good version.

Repeatable loads

Every load is an upsert. Running the pipeline twice gives the same result: the second run reports zero inserts and everything unchanged. The run summary also counts revised and late-filled values separately, so a changed number is visible rather than silently overwritten.

Lineage

Every row in SQL carries the id of the run that wrote it, and the catalogue shows the path from bronze to gold for the latest run. Each run also writes a small JSON file with status, quality results and merge counts.

Security and deployment

The Function reaches the data lake and the database with a managed identity, so there are no connection strings or passwords in the code or settings. GitHub Actions deploys with OIDC federation to Azure instead of stored credentials, and a failing test blocks the deploy.

Running cost is close to zero: Azure Functions Flex Consumption, the Azure SQL free offer and App Service F1 cover the workload.

What a real platform would change

This is a learning project with a small data volume. The transformations run in pandas inside a Function because that is free and enough for a few thousand rows a year. On a real platform the same logic would live in Databricks as Delta tables and a scheduled job, and the merge step is written so it can move there directly. The Django app deliberately has no database of its own: it reads the published data product, so a visit to the catalogue never wakes the SQL database.
